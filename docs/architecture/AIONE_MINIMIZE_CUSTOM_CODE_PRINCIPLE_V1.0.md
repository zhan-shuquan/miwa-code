# AIONE 最小自研代码原则｜V1.0

状态：CURRENT

生效日期：2026-08-30

适用范围：美和AIONE一体化工作平台（AIONE）全部前端、后端、基础设施、AI、自动化与集成建设。

## 1. 核心原则

AIONE长期坚持：

> 能复用成熟能力，就不自己开发；能配置，就不写代码；能调用标准组件，就不造组件；能用平台能力，就不做页面级实现。

目标不是让代码量最大，而是在保证业务正确、架构统一、安全可控和长期可维护的前提下，让AIONE自维护代码尽可能少。

判断任何新增实现前，默认先问：

> 这段代码真的必须由AIONE自己拥有吗？

如果答案是否定的，应优先采用成熟组件、标准协议、平台服务、API、配置、规则函数或外部集成，而不是新增自研实现。

## 2. 自研代码应主要保留在哪里

AIONE真正需要长期拥有和维护的代码，应集中在具有美和独特业务价值的部分：

- 统一业务对象与对象关系
- 美和业务规则
- 美和业务流程与状态机
- 权限与责任模型
- AI业务编排与Proposal机制
- 自动化编排
- 统一Contract与领域服务
- 必要的平台适配层
- 无成熟替代方案且已验证具有长期价值的核心能力

不应把工程资源长期消耗在成熟行业能力的重复实现上。

## 3. 优先复用的能力

以下能力原则上优先采用成熟方案，而非自研：

- UI基础组件：Material体系或其他成熟组件库
- 图标：Material Symbols等标准图标体系
- 登录与认证：Google或标准认证方案
- 文件：Google Drive、Cloud Storage等成熟文件能力
- 日历：Google Calendar
- 邮件：Gmail
- 通知：成熟通知机制与平台能力
- 表格、Tabs、Menu、Dialog、Drawer、Tooltip、Toast等通用交互组件
- 搜索：成熟搜索服务或统一搜索平台能力
- 日志与监控：Google Cloud Logging、Monitoring等
- 定时任务：Cloud Scheduler、Cloud Tasks等
- 消息队列与事件：Pub/Sub等成熟机制
- AI模型调用：通过统一AI Gateway接入OpenAI、Vertex AI等，不在页面内重复实现
- 外部业务能力：优先通过API、Connector、Plugin或Adapter接入

## 4. 技术选择优先级

面对一个新需求时，默认按以下顺序判断：

1. 是否已有AIONE共享平台能力可直接复用
2. 是否已有成熟第三方/Google能力可直接使用
3. 是否可通过配置完成
4. 是否可通过规则函数、数据库函数或API完成
5. 是否可通过Connector / Plugin / Skill完成
6. 是否需要传统自动化
7. 是否需要AI辅助判断
8. 是否确实需要新增自研代码

只有前面方案不适用，且新增代码具有明确长期价值时，才进入自研。

## 5. 前端约束

前端不得为了单页效果重复开发已有能力。

新增页面前必须先判断：

- 是否已有Page Type
- 是否已有共享母版
- 是否已有Shared Component
- 是否已有Business Component
- 是否可以通过配置与数据生成
- 是否应该修改Design Token而不是写局部样式
- 是否应该修改共享组件而不是复制组件

禁止长期形成：

- 每页一套组件
- 每页一套CSS
- 重复Dialog / Table / Tabs / Menu实现
- 页面级hardcode视觉变量
- 仅为某一页面存在的临时Patch

## 6. 后端约束

后端不得跟随页面数量线性增长。

优先形成稳定的：

API Layer
→ Application / Service Layer
→ Domain Layer
→ Repository / Data Access Layer
→ Database / External System

业务规则应集中在领域和服务层，不应散落在Controller、Route、API Handler、React页面或临时脚本中。

同一个业务对象不得因为不同页面而建立第二套逻辑、第二套字段或第二套API。

## 7. AI与自动化约束

AIONE不得为了使用AI而AI化。

- 确定性问题优先使用确定性技术
- 能规则化的先规则化
- 能函数化的先函数化
- 能API化的先API化
- 能自动化的先自动化
- 需要判断时再使用AI
- 需要最终责任时保留人工确认

AI模型调用必须尽量通过统一AI Service / AI Gateway完成，不允许各页面分别建立独立调用逻辑。

## 8. 引入自研代码的最低条件

新增自研代码至少应满足以下条件之一：

- 体现美和独特业务规则或方法论
- 是统一平台底座能力，能够被多个模块长期复用
- 外部成熟方案无法满足关键业务要求
- 对数据、安全、权限、审计或性能有必须自控的要求
- 已经过Product Freeze并确认不会只是临时方案

如果只是“做起来更快”“当前页面方便”或“外部方案还没研究”，不足以成为新增自研代码的理由。

## 9. 工程治理要求

以后在Architecture Review、Product Freeze和Code Review中，应增加一个默认检查项：

**Custom Code Necessity Check**

至少回答：

- 这段代码为什么必须由AIONE自己维护？
- 是否已有共享能力或成熟外部能力可以替代？
- 是否会形成第二套实现？
- 三年以后是否仍值得维护？
- 删除这段代码后，业务核心价值是否会受损？

如果无法合理回答，应优先删除、替换、整合或上移到共享平台层。

## 10. 长期目标

AIONE追求的不是“代码越来越多”，而是：

> 业务能力越来越强，但自维护代码占比越来越低。

最终希望形成：

**成熟平台能力 + 统一业务对象 + 标准页面类型 + 共享组件 + 配置 + 数据 + 规则 + AI编排**

而不是：

**大量页面 × 大量重复组件 × 大量重复CSS × 大量局部补丁。**

本原则作为AIONE长期Architecture Guardrail之一执行。
