保留 AIONE 现有页面风格、导航、身份系统、Cloud Run 与 Cloud SQL。参考成熟 ERP 的操作完整性，引入适合现有技术的开源组件；不以替换整个系统为前提。

## 4. 配置模型与边界

需要共同设计四层，而非仅增加“新增分类”按钮：

1. 分类：稳定 ID、编码、名称、所属之家、顺序、状态、内置或自定义。
2. 字段：稳定 ID、字段键、标签、类型、必填、默认、顺序、数值边界/精度/币种、引用来源。
3. 资料：稳定 ID、所属分类、字段值、顺序、状态、默认标记、版本与维护记录。
4. 绑定：来源分类、目标业务实体/字段、显示字段、引用 ID、默认带入规则、已有计算适配器。

第一轮字段类型限定为文本、数值、布尔、日期、单选和资料引用；不开放执行任意代码或 SQL。

“新增字段”有两种明确结果：

- 资料字段：保存于该分类，进入通用表单、列表、模板和导出。
- 业务扩展字段：通过已支持的扩展区域挂到商品页，并可保存/重新读取；不自动加入利润公式或平台上架请求。

要影响现有核算或平台字段，必须绑定已经实现、明确支持的适配器。新算法和新接口仍需开发。界面应显示“仅存资料”“已绑定商品”“参与现有核算”等实际状态，不能让用户误认为建字段后已生效于所有流程。

数据存放沿用现有 Cloud SQL。具体新增表及迁移编号在检查现有 schema 后确定；不把任意自定义对象直接塞入现有核算 payload，也不在浏览器建立第二份权威参数库。

## 5. 稳定 ID 与变更保护

- 修改显示名不改变资料 ID，已有商品保持引用；重名与编码冲突须明确提示。
- 迁移前统计旧名称引用；唯一匹配才能自动转换，缺失或歧义输出待处理清单，不能静默替换。
- 旧读写路径采用可验证的兼容过渡；同一资料只有一个权威值。核算适配器同步支持 ID，再逐步移除名称依赖。
- 已引用资料不可硬删除，可停用；已引用分类和字段同样保护。关闭资料分类不清空历史字段值。
- 字段已存资料后，类型与单位变更必须预检，不能直接把人民币解释为日元、文本解释为数值。
- 默认只影响新建或空值；已有商品不因全局默认变化而被覆盖。
- 保存包含版本、维护人和原因；冲突保留草稿，未保存离开时提醒。
- 设置变更不自动推送平台、不更改线上库存、不批量改价。

## 7. 同一轮完整交付的顺序

1. 核对现有分类、店铺、权限、历史模型；建立逐字段来源/消费者清单，避免重复建设。
2. 实现分类、字段、资料、绑定的基础存储、API 与通用编辑器；同时落实稳定 ID 与兼容迁移。
3. 完善列表、筛选、批量启停、动态 Excel 与历史查看；权限全部由后端执行。
4. 接通本轮商品字段、当前核算适配器与各之家入口；商品编辑中的未保存输入必须保留。
5. 在隔离环境用真实结构的样例资料整体验收，再进入预览验收；通过后按既有流程合并和上线。

可以分提交实现，但不把只完成按钮或孤立页面的中间版本宣布为业务完成。
